# Бесплатный источник для 200 трейдеров: результаты проверки 14 октября 2026

## Требование

200 отобранных трейдеров: активность за 60 дней, больше пяти сделок, winrate ≥60%, положительный P&L за 30 дней. Полные данные текущих позиций и доказанное время открытия. 500 пользователей приложения; 100 пользователей самостоятельно подключают свои Bybit API-ключи. Требование задержки до 3 секунд сохраняется; оно не заменяется показателем p95.

## Вывод

Найден и проверен бесплатный поток аккаунтов Lighter, который снимает ограничение Hyperliquid на 10 пользовательских подписок. Он является техническим кандидатом для нового отбора трейдеров. Все требования продукта одновременно ещё не подтверждены: 200 качественных трейдеров не отобраны, даты старых позиций не восстановлены, доставка в приложение и исполнение на 100 Bybit-аккаунтах не измерены. Нельзя объявлять решение готовым или гарантировать максимум 3 секунды по этому тесту.

## Живые измерения

Использован официальный публичный WebSocket `wss://mainnet.zklighter.elliot.ai/stream?readonly=true`, без ключей. Сначала шесть каналов trade, затем по одному account_all для 200 кандидатов, найденных в публичных сделках. Подписки отправлялись с интервалом 375 мс, ниже лимита 200 клиентских сообщений в минуту. Тесты длились 150 секунд, включая постепенное подключение. Это не 150 секунд наблюдения всех 200 одновременно.

| Измерение | Локальный Mac | Production Mac mini через существующий VPN wrapper |
| --- | ---: | ---: |
| Подтверждённые аккаунты | 200/200 | 200/200 |
| Записи исполнений в account_all | 3722 | 3373 |
| Получение исполнений, p95 | 266 мс | 271 мс |
| Получение исполнений, максимум | 1317 мс | 401 мс |
| Записи исполнений старше 3 секунд | 0 | 0 |
| Ошибки WebSocket | 0 | 0 |
| Получено JSON за весь тест | 182462359 байт | 161232207 байт |

Количество записей не равно количеству уникальных сделок: одна сделка может поступить обоим отслеживаемым участникам. Статистика измеряет `received_at - trade.timestamp`; сервер сообщает NTPSynchronized=yes, часы биржи отдельно не калиброваны. Последнее transaction_time в первоначальном снимке не принимается за момент получения свежего снимка.

Файлы доказательств:

- Локально: `backups/lighter-probe-1792006917398/report.json`.
- Сервер: `backups/lighter-probe-1792007170515/report.json`.
- Прямое серверное соединение без wrapper: `backups/lighter-probe-1792007032164/report.json`, нет подтверждений подписок, соединение закрыто с 1006. Причина не установлена; подключение напрямую нельзя считать рабочим резервом.
- В ранней версии отчёта accountsWithPositions означает наличие полей позиций/настроек, включая нулевые позиции. Это не доказательство 200 открытых позиций. В скрипте название исправлено, отдельно считается accountsWithOpenPositions.

В публичных снимках фактически получены размер, направление, средний вход, unrealized/realized P&L, liquidation_price, initial_margin_fraction, allocated_margin, margin_mode и funding. В 1829 новых рыночных исполнениях серверного теста присутствовали before-position, before-entry и timestamp для обеих сторон. Три проверенных обычных аккаунта (702384, 270812, 759238; account_type=0) вернули историю trades HTTP 200 без ключа и next_cursor. Это расходится с описанием REST trades, где для обычных аккаунтов указана авторизация: доступность дальнейшей истории пока не гарантирована.

Проверены публичные 30-дневные pnl для двух аккаунтов. Первые две страницы официального pnlLeaderboard (30d, limit=100, offset=0/100) дали 200 записей с положительным P&L. Они не приняты как 200 подходящих трейдеров: winrate, полнота истории и независимость ещё не проверены. Нельзя переносить результат рейтинга на существующие Hyperliquid-адреса.

## Что ограничивает остальные варианты

- Hyperliquid public trades быстро передаёт адрес, время, цену и размер, но не startPosition, комиссии, плечо, залог и все события ликвидации/изменения аккаунта. Код collector уже использует этот канал и дозапрашивает userFills. Один этот канал не доказывает полноту позиций.
- Hyperliquid разрешает 10 уникальных пользователей в пользовательских WebSocket-каналах на IP. Поллинг clearinghouseState для 200 адресов раз в 3 секунды требует минимум 8000 weight/min только для одного perp scope, против официальных 1200. Поллинг userFills требует ещё больше: базовый вес 20.
- Dwellir бесплатный Index пригоден для дозагрузки ограниченного объёма; полный gRPC поток платный. 0xArchive имеет ограниченную бесплатную квоту. Chainstack бесплатный план не подтверждает необходимые пользовательские HyperCore-потоки и объём. Alchemy HyperCore находится в private preview. Эти сервисы не приняты как бесплатное production-решение требований.
- Своя Hyperliquid-нода даёт fills и состояние, но требует подходящего оборудования и эксплуатации; это не вариант без новых расходов на текущем Mac mini.

## Архитектура, которую следует испытывать

1. Отдельный адаптер Lighter: публичные account_all выбранных 200 аккаунтов плюс общий поток market_stats. История и сверка идут отдельно от live. Существующую базу Hyperliquid не заменять непроверенными кандидатами.
2. Внутренняя идентичность включает platform/account/subaccount/market. Размеры и деньги сохраняются десятичными строками; время в микросекундах нормализуется явно. initial_margin_fraction в живом ответе и примерах документации имеют разные представления, требуется проверка единиц.
3. Durable журнал исполнений; канонический ключ с идентификатором аккаунта и исполнением. Позиции сверяются со снимками; начальная дата подтверждается исходным открытием, а не последним изменением аккаунта. Переподключение требует дозагрузки и проверки разрывов.
4. Рыночные и позиционные обновления часто приходят тысячами сообщений в секунду. В памяти сохраняется последнее состояние; исполнение записывается один раз. Не выполнять SQLite-транзакцию и рассылку 500 посетителям для каждого изменения P&L. Выдавать изменения для видимой страницы, детали открытого профиля и общие цены.
5. Bybit-исполнитель получает подтверждённое изменение позиции напрямую с сервера. Для 100 пользователей параллельно рассчитывается их бюджет, проверяются ограничения цены и текущие позиции. Выставление и исполнение ордера имеют отдельные времена. Предыдущий бюджет задержки не является измерением.
6. Приёмка измеряет всю цепочку: исполнение источника → запись → отображение; отдельно исполнение источника → принятие Bybit → исполнение Bybit. Проверяются 500 сессий и 100 тестовых исполнителей, серия быстрых fills, частичные исполнения, повторные события, переворот и перезапуск. Реальные деньги не включаются в исследовательский тест.

## Нерешённые условия

- Lighter документирует readonly-подключение для чтения из ограниченных регионов, однако Terms of Service распространяются на API и исключают, среди прочих, резидентов РФ. Доступность readonly не доказывает разрешение использования в конкретной юрисдикции или в платном сервисе. Требуется разрешённая схема доступа/уточнение у провайдера; новые тесты через смену IP не используются как доказательство разрешения.
- Каналы чужих ордеров требуют auth; публичные позиции и сделки не означают доступ ко всем чужим активным ордерам/отменам.
- Публичный источник и Bybit не дают абсолютного ограничения времени исполнения. Собственная система может отсекать устаревшие сигналы, но пропуск сигнала должен считаться нарушением требования копирования, а не успешным исполнением ≤3 секунд.
- 200 участников теста не имеют подтверждённого winrate ≥60%. Старые времена открытия, 60-дневное покрытие и пригодность для копирования пока не доказаны.
- На production выполнен только read-only диагностический тест; интеграция Lighter и автоторговля не установлены. Production процессы не перезапускались, .env.local и рабочая SQLite не изменялись.
