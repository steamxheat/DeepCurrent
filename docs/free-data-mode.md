# Только бесплатные источники

Пользователь подтвердил: без платных поставщиков данных и аренды. Это ограничение расходов, а не разрешение обходить лимиты API. PostgreSQL/Redis — бесплатное ПО; вопрос их миграции остаётся отдельным незавершённым пунктом этапа 6.

## Рабочая схема

1. Один collector получает публичные market trades и фильтрует по индексу кошельков. Уведомление BUY/SELL не объявляется Open/Close без `startPosition`.
2. Десять userFills-подписок имеют приоритет: видимые страницы, избранное, недавно активные адреса рейтинга. Свободные слоты перераспределяются по фактическим market trades; для фоновых адресов минимальное удержание 60с предотвращает постоянную переподписку. При нескольких пользователях это десять адресов **всего на IP**, не каждому пользователю. Смена вкладки меняет приоритет, а не повышает лимит.
3. Новый рыночный fill вне personal-set попадает в отдельную очередь коротких `userFillsByTime`-запросов. Все fills одного адреса объединяются в один pending запрос; 250мс debounce. Два обработчика, приоритет active/favorite. Нет полной загрузки 2000 старых fills на каждое рыночное событие.
4. В общей HTTP очереди один слот и 20 units оставлены для срочных подтверждений. Графики/исторические ордера/funding идут ниже. Большой backfill резервирует и дополнительный вес ответа, чтобы не истратить срочный резерв незаметно.
5. Пустой ответ API не подтверждает observed fill: он остаётся observed, запрос повторяется с backoff. История/разрывы восстанавливаются отдельным низкоприоритетным процессом; неудавшаяся задача не теряется.
6. Перезапуск/обрыв атомарно помечает существующее покрытие как gap; для невиденного адреса не создаётся ложная история. Подтверждение короткого fill не означает полноту истории или подтверждённую дату открытия всей позиции.
7. Фоновые snapshots не блокируют отдельный цикл видимых профилей. Просматриваемые данные требуют свежего scope; сам факт старой WS-подписки не отменяет необходимую REST-сверку.

Быстрый запрос подтверждает только поля, реально возвращённые API. По сохранённому снимку можно оценить изменение signed size, но не доказать отсутствие пропущенных исполнений, funding/liquidation/иного изменения. Поэтому такое предположение не записывается в raw как биржевой `startPosition` и не используется как exact-сигнал.

## Честные пределы

- Лимит публичного API: 10 unique user subscriptions, общий REST weight 1200/мин на IP. Наш рабочий refill 600 units/мин оставляет запас; максимальный начальный burst 150.
- Один fill-history запрос стоит 20 units плюс вес returned rows; 600/20 = 30 запросов/мин **до** снимков, backfill и дополнительного веса. 1000 активно торгующих разных адресов нельзя подтверждать каждую секунду таким опросом. Слияние событий одного адреса улучшает реальные условия, не отменяет математику.
- Быстрый путь ограничен очередью 1000 адресов и окном 60с; старые задачи остаются для обычного recovery. `expired`/`rejected` видны в диагностике, события raw не удаляются.
- Цель ≤3с возможна для наблюдения и части подтверждений при умеренной нагрузке; гарантировать exact-охват всех 1000 бесплатно нельзя.
- Несколько браузеров/аккаунтов с тем же выходным IP не увеличивают установленный IP-лимит. Новые платные сервисы, VPS и VPN не подключаются.

## Проверка

`npm test`, `npm run lint`, `npm run build`: 92/92 теста. Новые тесты покрывают coalescing, in-flight + следующий fill, приоритет, bounded queue, backoff, 429 cooldown, reserve slot/weight, API-error retry, сохранение recovery gaps, мгновенную observed-публикацию без ложного exact и выбор десяти stream-адресов. Линтер и сборка проверяются после изменения.

Observed событие публикуется атомарно вместе с новым raw fill и не ждёт тяжёлого replay. Пересчёт позиции остаётся в durable очереди. Поздний API-fill исправляет **ту же** строку, а не создаёт вторую сделку. Текущие exact-позиции и уведомления не используют observed-событие как доказательство открытия.

`npm run check:journal -- <начало-прогона-в-миллисекундах>` показывает очередь подтверждений, backlog, known/unknown, задержки внутри и вне текущего personal-set. В разделе latency только подтверждённые строки; рядом есть количество неподтверждённых, чтобы медленные адреса не исчезли из отчёта.

Дополнительно 32/32 теста очереди/HTTP budget/replay/выбора streams прошли на Mac mini Ubuntu, в изолированной временной базе; рабочие сервисы не менялись.

Запуск остаётся shadow по умолчанию. Production не переключён; 24–72h soak, внешние уведомления и нагрузка 1000 различных страниц ещё не приняты.

Измерение 13 октября в shadow, после отдельной observed-публикации, до адаптивного выбора stream-адресов: 1000 SSE соединений / 60с, 0 ошибок; 222 distinct events от 24 адресов; p95 первого показа 688мс, server emit→client 39мс. Обогащённые exact updates только двух адресов за минуту имели p95 37 993мс — это не показатель всех 1000.

Диагностика за 109с того же запуска: 444 live fills вне personal-set, из них 112 получили authoritative fields (6 адресов); p95 подтверждения 58 935мс. На момент замера ещё 24 pending адреса, 20 задач быстрого окна expired и 60 history-recovery задач; integrity ok, conflicts 0. Эти ограничения не скрыты за низкой observed-задержкой. История может ждать на нижнем приоритете при постоянном потоке; её нельзя объявлять complete.

После адаптивного выбора streams: 1000 SSE / 60с, 0 ошибок, 342 distinct events от 28 адресов, exact updates от 9 адресов; p95 первого показа 1094мс, confirmed revision 43 395мс (включает подтверждение ранее observed fills из subscription snapshot). Это другой интервал активности, не контролируемое сравнение прироста. Через 85с collector подтвердил 871 рынок и 10 user subscriptions; integrity ok, conflicts 0, projection backlog 0. При этом 30 адресов ещё в confirmation queue, 8 expired, 62 recovery задачи. Полная точность/история всех 1000 не достигнута.
