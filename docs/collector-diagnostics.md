# Диагностика без открытого чата

Сборщик самостоятельно сохраняет диагностику в SQLite `collector_health`. Чат, браузер и компьютер разработчика не нужны, если сборщик установлен и запущен на сервере под PM2. Этот код пока локальный: до установки на сервер новые записи там не появятся. Telegram не требуется.

## Что записывается

- Run ID и время каждого запуска/остановки, открытия и закрытия WebSocket, код закрытия, clean/abnormal, длительность отключения внутри одного запуска, число запланированных подписок. Новые подключения не означают, что вся история уже восстановлена.
- Каждый выполненный HTTP-запрос: операция, публичный адрес кошелька, приоритет, номер попытки, HTTP-код, сетевое время, очищенная ошибка. 429/5xx и отдельные повторные попытки видны. Время ожидания очереди не включено в сетевую длительность; очередь измеряется отдельно.
- Восстановление истории: адрес, число fills, время, полнота доступного интервала. Ошибки подтверждения, снимков по DEX scope, портфеля/ордеров/funding, подписок, разбора сообщения, проекции и доставки уведомлений.
- Для исключений сохраняется очищенный stack trace (до 2000 символов), чтобы найти функцию и строку, а не только текст ошибки. Произвольные тела ответов и закрытые данные не записываются.
- Одинаковые ошибки в течение 10 секунд объединяются в запись с `repetitions` и `lastOccurrence`: поток одинаковых отказов не вытесняет диагностику мгновенно, число повторов не теряется.
- Ошибочные/conflicting fills: до 10 примеров в batch с адресом, монетой, ID и причиной; общий счётчик включает все ошибки. Повторные неизменённые fills считаются отдельно и не объявляются ошибкой.
- Раз в минуту: подключение, возраст последнего сообщения, задержка heartbeat, pending/active HTTP, cooldown, recovery backlog, возраст/просрочка/отказы очереди подтверждений, охват рынков/точных подписок, RSS/heap, свободный диск и накопленные счётчики fills.
- Отчёт дополняется текущим backlog проекции, причинами неизвестных позиций, состоянием покрытия истории, ошибками/возрастом снимков и очередью доставки.
- Отдельно p50/p95/max приёма и подтверждения, включая задержки выше 10 секунд и число ещё неподтверждённых fills. Ограничение 100 000 последних non-history fills явно отмечается; это не покрытие всех адресов и не скорость доставки в браузер.

Токены, headers, cookies, тела запросов, Push endpoints и содержимое уведомлений не записываются. Времена — Unix milliseconds; адреса публичные. Доступ к БД/отчёту только у администратора сервера: публичного endpoint нет. Не отправлять всю БД сторонним сервисам.

## Как получить отчёт позже

Из каталога проекта с тем же `DEEPCURRENT_DB_PATH`, который использует сборщик:

```sh
npm run report:collector -- 24
node scripts/check-journal.mjs
```

Первая команда: события и сводка за последние 24 часа (можно указать до 720 часов). Вторая: отдельно текущая целостность/конфликты и задержки fills за последние 10 минут. Обе читают БД без записи и не обращаются к бирже/Telegram/Push. Скопировать вывод в этот чат и написать «разбери журнал сборщика». Подробный отчёт выводит до 1000 последних ошибок/медленных запросов/переходов; HTTP-сводка учитывает все сохранённые запросы в окне.

Диагностика ограничена 30 днями **или 100 000 записей**, что наступит раньше; при большом количестве HTTP-запросов фактическое окно может быть значительно короче. `retainedFrom` показывает первую сохранённую запись. Очистка раз в минуту удаляет только старую диагностику, не торговую историю; между очистками лимит может кратковременно превышаться. Для долгого расследования регулярно сохранять отчёт вне БД.

## Что нельзя определить только этими логами

При отключении электричества/SIGKILL процесс не успеет записать причину: будут видны обрыв heartbeat и новый run ID; точную причину искать в PM2/system journal. Минутные выборки не равны uptime% и могут пропустить краткий stall. Снимки непросматриваемых кошельков намеренно обновляются редко — возраст >30с не обязательно ошибка. `recovery_ok` с `complete=false` означает успешный запрос с неполным покрытием, а не полное восстановление. Нет гарантии полных fills всех 1000 адресов или ≤3с.

Код проверяется быстрыми тестами: сохранение run IDs, disconnect/reconnect, пробелы heartbeat, cooldown, ограничение хранения без удаления торговых данных, редактирование секретов, HTTP success/error и отказ самого диагностического writer. Настоящий длительный прогон остаётся проверкой сервера: ждать можно без открытого чата.
