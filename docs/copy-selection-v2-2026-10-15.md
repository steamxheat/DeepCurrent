# Отбор для копитрейдинга: новая постановка, 15 октября 2026

Это журнал доказательств, не заявление о готовых 100–200 трейдерах.

## Действующие требования

- Не менее 5 уникальных торговых действий за 60 дней.
- Общий winrate не ниже 60% по завершённым жизненным циклам всей доступной истории. Частичные закрытия — не отдельные победы.
- Положительный официальный накопленный PnL за всё время.
- Оборот не менее $300 000 за последние 30 дней, не за сутки.
- Доказанные начало и размер текущих позиций; все субаккаунты адреса, комиссии и funding.
- Индивидуальные исполнения и позиции через публичный API/поток; отдельное измерение доставки до 5 секунд. ACK, снимок, HTTP-duration и обновление заявки не доказывают задержку исполнения.
- Минимум 20 закрытий отменён пользователем. Размер выборки показывается, малая выборка не называется доказательством сильной стратегии.

Production, торговля, рассылки и `.env.local` не затрагиваются. Предварительные адреса в приложение не добавлены.

### Поле с названием net не гарантирует чистую прибыль

Проверен [исходный расчёт tradeHistory](https://github.com/dydxprotocol/v4-chain/blob/main/indexer/services/comlink/src/lib/trade-history.ts). `netRealizedPnl` там накапливает gross closing PnL; `netFee` — отдельную накопленную комиссию. Для предварительной проверки цикла используется `netRealizedPnl − netFee + signed netFunding` сопоставленной закрытой позиции.

Это **не независимая проверка всех raw fills**. `tradeHistory` использует максимум100000 fills; профили с totalResults>=100000 не принимаются как полные. Builder/router fees дополнительно по всем исходным исполнениям ещё не сверены. Старое `perpetualPositions.realizedPnl` может быть нулём при ненулевом gross расчёте истории: контроллер подставляет0 при отсутствующем totalRealizedPnl. Такие нули не используются как доказательство финансового результата.

## Следующая доказательная проверка

1. Завершить небольшой пилот, разобрать needs_review: ошибка парсера, неполнота или реальное расхождение источника.
2. Если появляются подходящие reported-профили — независимый полный replay raw fills, отдельная проверка builder/router fees и funding. Не выдавать использование одного серверного расчёта за ручную сверку всех сделок.
3. Для осмысленной активной выборки наблюдать **новые исполнения** с идентификаторами и exchange timestamps; сохранять максимумы/превышения/потери и разрывы. Отдельно учитывать погрешность часов.
4. Только после этих ворот расширять discovery, в первую очередь по свежим публичным chain-исполнениям, а не бесконечным неактивным рейтингам.
5. Reconnect/backfill и приложение под500 пользователями/100 копирующими аккаунтами — отдельная приёмка, ещё не выполнена. Абсолютный будущий максимум5 секунд не обещан.

## Независимый raw-fill replay

Созданы `src/lib/dydx-raw-audit.ts/test.ts` и `scripts/audit-dydx-raw.mjs`. История фиксируется по latestProcessedBlockHeight начального снимка, проверяется фактический блок, /fills читается с createdBeforeOrAtHeight и page. [Официальный controller](https://github.com/dydxprotocol/v4-chain/blob/main/indexer/services/comlink/src/controllers/api/v4/fills-controller.ts) задаёт eventId ASC для page-пагинации. Внутри одного timestamp сохраняется этот канонический порядок, а не порядок UUID. Offset за25000 не запрашивается; raw count>26000 остаётся needs_review.

Аудит не использует tradeHistory PnL: самостоятельно рассчитывает жизненные циклы, распределяет комиссии при flip, сопоставляет funding по завершённым позициям, проверяет authoritative startPosition и начальный снимок size/opening/entry. Ненулевые builder/router fees требуют отдельной сверки, а не считаются нулём. Числа около погрешности расчёта остаются needs_review. Денежные пороги оборота суммируются десятичной арифметикой.

Проверено различие API entryPrice и PnL-базы оставшегося объёма. В реальном fill288effe9-009b-53ec-b44c-b84775334608 API62484.54168394857 совпал со средним всех открывающих исполнений, а не remaining-inventory62484.603537532355. Разделены displayAverage и PnL-average; добавлен регрессионный тест с частичным закрытием и последующим увеличением. Это различие определения показателя, не доказательство неправильного исполнения биржей.

`backups/dydx-raw-jqj-20261015/report.json`:23367 исходных исполнений полностью прочитаны до высоты109572841,6 завершённых циклов/1 победа (16.66667%), официальный PnL+1298.145744, оборот30д193796.9669. Одна текущая позиция совпала. Адрес rejected по новым требованиям. 23367 исполнений не превращены в23367 завершённых позиций. Срез исторический, не continuously-fresh профиль. Это независимый программный replay, не ручной разбор каждого трейда.

## Не исключать Hyperliquid по неправильному основанию

[Официальный лимит](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/rate-limits-and-user-limits) —10 unique users для user-specific WS, не для всех публичных рыночных trades. [Публичный WsTrade](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/websocket/subscriptions) содержит buyer/seller addresses. Поэтому гибрид public trades → адресный REST для ограниченной низкоактивной выборки можно отдельно исследовать без ротации IP. Это гипотеза, не готовая замена: в public trade отсутствуют startPosition/fee/closedPnl, а полный REST стоит20+вес ответа при бюджете1200/мин. Сначала измерить реальную частоту событий выбранных адресов, очереди и полноту рынков/разрывов; не обещать<=5с и не возобновлять старые production workers по этому пункту.
