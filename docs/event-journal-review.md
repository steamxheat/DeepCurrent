# Проверка аудита и архитектуры журнала Deep Current

Дата: 13 октября 2026. Основание: `docs/phase-1-audit.md`, текущий код поверх `55a3d5c`, официальные схемы Hyperliquid. Это проверка проекта решения; новый collector ещё не реализован.

## Вердикт

Основные P0 выводы подтверждены кодом. Направление «сначала устойчивый журнал, затем расчёт позиций и интерфейс» верное. Исходную архитектуру нельзя реализовывать буквально без поправок ниже: общий watermark недоступен из имеющихся источников, порядок нельзя получать из tid, соединения SQLite сейчас разные, а внешняя доставка не может гарантировать отсутствие дублей после любого сетевого сбоя.

Масштаб проектирования: 1000 наблюдаемых адресов, один collector на имеющемся сервере, в перспективе 1000 одновременных пользователей. Такой масштаб здесь не протестирован. Производственные числа из первого аудита остаются историческими замерами, повторно в этой проверке не измерялись.

## Подтверждение выводов

Повторно выполнены шесть автономных проверок чистых функций, без записи в БД и сетевых запросов к торговому API:

Подтверждены по цепочке вызовов:

- `scripts/bot.mjs:121`: частичные успешные ответы DEX заменяют состояние всего кошелька; `readyWallets` выставляется даже при отказе части DEX.
- `scripts/bot.mjs:305`: reconnect пересоздаёт соединение и делает seed, но не восстанавливает fills. Функция `syncExactHistory` получает orders/funding, а не fills.
- `scripts/bot.mjs:249`: exact назначается рыночной производной без подтверждённой непрерывности.
- `src/lib/event-store.ts:101` и `src/lib/hyperliquid.ts:319`: дедупликация по разным строковым ключам не объединяет REST fill и market group.
- `src/lib/event-store.ts:203`: последняя запись выбирается по wallet/coin, без подтверждения принадлежности текущему полному снимку scope.
- `src/app/wallet/[address]/page.tsx:56`: неизвестная длительность привязана к общему началу истории кошелька, которое не доказывает возраст конкретной позиции.
- `src/lib/hyperliquid.ts:107`: импорт использует aggregateByTime=true, непригодный как канонический журнал отдельных fills; старые агрегаты нельзя выдавать за raw.

Остальные продуктовые пункты аудита остаются списком для последовательной реализации. Здесь не повторялись все браузерные сценарии, live-проверка 50 адресов и production-замеры.

## Обязательные поправки к архитектуре

### 1. Транзакции должны использовать одно соединение

Что проверено: `event-store.ts:35` и `notification-store.ts:34` открывают отдельные `DatabaseSync` одного файла. BEGIN на первом не делает записи второго частью транзакции; вызов второго writer внутри первого может ждать блокировку.

Решение: один владелец соединения на процесс для согласованных записей. Выделить существующее открытие БД в общий модуль, дать journal writer одну явную границу транзакции. Не вызывать функции с собственным BEGIN изнутри этой границы. Web может иметь своё соединение, но не выполнять ingestion. Пользовательские настройки продолжают сохраняться отдельно.

Если пропустить: обещанная атомарность останется фиктивной; возможны потеря событий и блокировки.

### 2. Сохранение входных данных и расчёт состояния — две устойчивые стадии

Что исправляем: формула «raw + cursor + state + outbox всегда одной транзакцией» плохо работает для позднего fill и неоднозначного порядка. Нельзя отвергать исходное событие из-за невозможности сразу вычислить позицию.

Решение: транзакция A сохраняет raw evidence и прогресс получения. Транзакция B сохраняет вычисленное состояние, lifecycle-события, прогресс обработки и намерение уведомления. Для простого последовательного события разрешено объединение, но оба прогресса остаются разными. Необработанное raw после crash подхватывается снова. Внутри транзакции нет await/network.

Если пропустить: сложные события будут теряться или неправильное состояние закрепится ради продвижения курсора.

### 3. Идентичность и порядок — разные вещи

Базовый ключ исполнения: `(network, wallet, canonical_market, exchange_time, tid)`. Wallet обязателен: одна рыночная сделка может затронуть двух наших трейдеров. Canonical market сохраняет исходную идентичность DEX/spot/perp; красивое название используется только для отображения.

`tid` — хеш, не последовательный номер. Для одного времени сортировка по tid допустима для стабильного отображения, но не доказывает порядок переходов позиции. При наличии startPosition связывать before/after; при нескольких допустимых цепочках сохранять неопределённость. Порядок доставки и локальный ingest_id также не являются порядком биржи.

Без tid запись получает статус unresolved identity и сохраняет raw payload. Не склеивать две сделки лишь по одинаковым цене, размеру, времени и hash. Обогащение REST не должно второй раз применять дельту уже известного market fill. Конфликт цены/размера одного ключа сохраняется как conflict, а не молча перезаписывается.

Если пропустить: replay будет устойчиво воспроизводить неверную последовательность, а часть fills исчезнет.

### 4. Общий точный watermark нельзя предполагать

REST-снимки нескольких DEX и WebSocket не дают нам доказанного общего атомарного состояния. ReceivedAt не равен exchange time. Одинаковый размер до и после reconnect не доказывает непрерывность: трейдер мог закрыть и заново открыть ту же сторону.

Решение: scope = network + wallet + DEX/spot; сохранять requestStartedAt, receivedAt, sourceTime при наличии, последний проверенный диапазон и причину gap. Buffer сохранять на диск с начала подписки. Получить scoped snapshots и overlapping history, согласовать цепочку before/after с состоянием. Если согласовать нельзя, размер можно показывать как snapshot, openedAt остаётся неизвестным. Старое openedAt не переносить только на основании совпадения знака позиции.

Если пропустить: появятся двойные дельты и прежние одинаковые либо устаревшие времена открытия.

### 5. Backfill не обещает восстановить недоступную историю

Использовать aggregateByTime=false. Фиксировать запрошенный интервал, границы ответа и насыщение лимита. Inclusive overlap устраняет обычную потерю на границе; cursor продвигается только после доказанного покрытия. При насыщении интервал делится. Если даже одна миллисекунда заполняет лимит и следующую часть нельзя получить, отмечать unrecoverable gap, а не увеличивать timestamp и объявлять успех.

Документация ограничивает доступную историю; короткий ответ сам по себе не доказывает историю от рождения аккаунта. Отдельно хранить доступность периода и согласованность жизненного цикла. Старые неизвестные даты могут остаться неизвестными; для большего охвата потребуется отдельный проверенный архивный источник.

Если пропустить: «история полная» снова будет недостоверной.

### 6. Точность определяется по полям

У одного события могут быть точные время/цена/размер, неизвестные fee и beforeSize, а у текущей позиции — неизвестное openedAt. Единственный precision на всю строку это не выражает.

Решение: source/evidence для исполнения; отдельно position continuity, opening evidence/reason и snapshot freshness. Проверенный fill со startPosition=0 подтверждает собственное открытие, но принадлежность этого открытия текущему lifecycle требует связной истории. Сам по себе market stream без гарантии полноты не получает статус exact lifecycle.

Полный успешно полученный snapshot scope заменяет current membership атомарно, включая пустой список. Отсутствующая позиция означает «в этом снимке отсутствует», а не точное CLOSE со временем снимка. Failed scope сохраняет прежние данные с возрастом и ошибкой.

Если пропустить: интерфейс и уведомления будут снова обещать больше, чем известно.

### 7. PnL и комиссии требуют явных единиц

Хранить исходные decimal строки, token комиссии и валюту расчёта; количество для проверки нуля сравнивать в точных единицах рынка. Не строить lifecycle на произвольном epsilon для Number. UI-округление не используется в расчёте состояния.

Gross realized PnL, trading fee и funding — отдельные величины. Fee в валюте расчёта вычитается; rebate увеличивает результат. Неизвестная конвертация не превращается в ноль. Builder fee уже входит в fee. При Flip исходный fill один, lifecycle-части две; распределение комиссии по закрываемому/открываемому количеству должно сохранять общую сумму. Неизвестная исходная себестоимость остаётся null после Add.

Поправка к пункту 19 первого аудита: при положительной fee и отсутствии clamp текущая формула `gross + fee - abs(fee)` фактически отменяет комиссию. Поэтому утверждение «всегда дважды вычитается» неверно. После исправления знака простым `+` → `−` появится двойное списание, если оставить feeBps. Комиссия оригинального трейдера и оценка комиссии копирующего должны иметь разные определения; вычислять каждую ровно один раз.

Если пропустить: рейтинг и Copyability останутся неверными даже после ремонта журнала.

### 8. Outbox не обеспечивает exactly-once во внешнем Telegram

Одна транзакция связывает derived event и intent уведомления; отдельный worker выполняет доставку. Уникальность `(event_id, recipient, channel)` защищает очередь, а unique inbox key — центр уведомлений. Worker хранит attempts, lease, nextAttemptAt, providerReceipt и результат. Ошибка одного получателя не блокирует остальных.

Сценарий: провайдер принял сообщение, процесс упал до сохранения ответа. Без поддерживаемого провайдером idempotency key повтор может дать дубль; отказ от повтора может потерять сообщение. Зафиксировать at-least-once внешнюю доставку с редким риском дубля, не обещать невозможную гарантию. Provider receipt не означает прочтение пользователем.

Исторический backfill, миграция и shadow replay по умолчанию не создают live-уведомлений. Late correction обновляет существующее состояние/карточку; новый сигнал допускается только по явной политике возраста и подтверждения. Настройки и подписка перепроверяются перед отправкой.

Если пропустить: импорт прошлого засыплет пользователей старыми входами или будут скрытые потери доставки.

## Минимальный контракт хранения

Названия ориентировочные; это контракт для миграции, не SQL, который нужно исполнять на production.

| Сущность | Ключ и обязательные данные | Инвариант |
|---|---|---|
| raw observations | ingest_id; canonical fill key nullable; source; raw payload; exchange/receive/persist time; import/live mode | Evidence не теряется при ошибке расчёта; повтор одного payload не раздувает журнал |
| canonical fills | составной ключ исполнения; revision; raw decimal fields; feeToken/oid/startPosition nullable; evidence references | Обогащение не создаёт новое исполнение; conflicting evidence сохраняется |
| ingestion coverage | network/wallet/scope/feed; полученные интервалы; gaps; retry/error; session status | latest timestamp не равен complete-through |
| snapshot batches + members | batch_id; scope; request/receive/source times; success/full status; позиции | Даже пустой успешный batch существует; только полный batch заменяет membership своего scope |
| position projection | wallet/market; signed size; lifecycle_id; openedAt nullable; field evidence; projection revision/input checkpoint | Разрыв не превращается в новое открытие; нулевая позиция не становится SHORT |
| lifecycle events | stable event ID; fill references; OPEN/ADD/REDUCE/CLOSE/FLIP legs; algorithm version | Replay одной версии даёт тот же результат; исправленный revision не удваивает объём |
| notification outbox | event/recipient/channel unique; payload; state/lease/attempts/nextAttempt; receipt | Работа переживает restart; history/shadow не отправляется |

Orders, funding и ledger остаются отдельными существующими типами, с provenance и coverage при развитии импорта; они не попадают в торговый объём. Не нужно превращать весь проект в универсальную event-sourcing платформу. Существующие user settings, favorites и inbox сохраняются.

Хранилище на этапе 2: SQLite WAL, короткие транзакции, один ingestion writer и ограниченная очередь запросов. Общий rate limiter, single-flight на один scope и приоритет active viewer/favorite. Если backlog не помещается/диск заполнен, явно unhealthy и gap, а не молчаливый drop. PostgreSQL/Redis — отдельное решение после измерений записи, чтения и retention на Mac mini.

Retain raw отслеживаемых кошельков; не сохранять все сообщения всех рынков бесконечно. Нужны измеряемые bytes/day и бюджет свободного диска. Нельзя чистить source evidence раньше зависимых расчётов без проверенного архива. Позднее исправление пересчитывает только затронутый wallet/market от проверенного checkpoint.

## Безопасная миграция и границы следующего этапа

1. Зафиксировать schema version и сделать консистентный backup; проверить restore в отдельный файл.
2. Создать новые таблицы аддитивно. Старые wallet_events, snapshots, позиции и настройки оставить для rollback.
3. Legacy market group и агрегированные userFills импортировать как legacy evidence. У них нет гарантированного набора raw IDs; не подделывать его и не пересчитывать из них точные финансовые итоги.
4. Новый writer в shadow сохраняет наблюдения и raw fills, одинаково обрабатывает REST/WS/reconnect, не отправляет уведомления. Не запускать второй collector с неконтролируемо удвоенным API-потреблением.
5. Проверить raw journal и recovery; затем этап 3 реализует общий reducer состояния. Старые экраны пока читают прежнюю модель.
6. Пересчитать производные показатели новой версией, сравнить счётчики и расхождения; переключать потребителей по одному. Backfill не приводит к массовой отправке уведомлений.
7. Rollback переключает чтение/обработчик назад, сохраняя новые raw данные. Не восстанавливать старый backup поверх новых событий; restore допустим только как отдельно согласованное аварийное восстановление.

Этап 2 заканчивается работающим устойчивым raw journal в shadow и тестами восстановления. Изменение ленты, Copyability, всех сортировок и deployment не входят в эту контрольную точку. Этап 3 — единый расчёт жизненного цикла и исправление финансовой арифметики; затем подключение потребителей.

## Проверки, без которых контрольную точку не проходить

- REST + WS + 3 reconnect → одно исполнение; новые поля обогащают его без повторной дельты.
- Два tid при одинаковых цене/времени/размере → два fills; один trade между двумя отслеживаемыми адресами → исполнение каждого адреса.
- Crash после записи raw и до projection → событие подхватывается; crash внутри projection → полный rollback; повторное выполнение не меняет итог.
- BUY/SELL одной миллисекунды с разным порядком получения; неоднозначная цепочка не получает exact.
- Reconnect с Close→Open той же стороны и размера не сохраняет старое время открытия.
- Один DEX упал, второй вернул пустой успешный scope: очищается только второй; первый сохраняет stale состояние.
- Страница API заполнена на границе времени; overlap не теряет fills; недоступная часть остаётся gap.
- Поздний fill и последующее enriched evidence воспроизводимо пересчитывают затронутую позицию.
- Ошибочный/нулевой размер, NaN, неправильный адрес, неизвестный market, конфликт одного ID не портят projection; evidence и причина отказа сохранены.
- Decimal zero, fee/rebate, другая fee currency, partial Reduce, Flip, неизвестная начальная себестоимость и нулевой gross с комиссией покрыты отдельными финансовыми тестами этапа 3.
- History/shadow не отправляет уведомления; outbox переживает timeout/crash, inbox остаётся единственным.
- Миграция и rollback проверены на копии БД; настройки/favorites не потеряны; нагрузка не блокирует чтение на длительные транзакции.

Для конечной цели p95 ≤3с измерять отдельно observed fill, подтверждённый lifecycle, отображение страницы и приём уведомления провайдером. Указывать охват и процент unknown рядом с latency. Повторный load test на 1000 пользователей нужен перед обещанием такой мощности.
