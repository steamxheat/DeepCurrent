# Новый журнал: безопасное переключение

**Это подготовленный runbook, не сообщение о выполненном deployment.** Полная цель этапов 5–6 ещё не принята: см. `stages-2-6-results.md`. Не включать live-уведомления, опираясь только на build/tests.

## Перед изменением production

1. Проверить exact commit, branch/origin, чистое дерево; сохранить предыдущий SHA. Не делать `reset --hard`, `git clean`, `npm audit fix` или автоматически стирать пользовательские файлы.
2. Проверить, что запущен ровно один web и один collector; записать фактические PM2 names/command/cwd. На действующем Ubuntu сервере это `dc-pulse-web` и `dc-pulse-bot`; не создавать второй collector под другим именем.
3. Не читать, не копировать и не менять `.env.local`. Сохранить существующее окружение процессов PM2; не печатать токен/прокси/VAPID в лог или чат. VAPID не генерировать заново при обновлении.
4. Использовать Node 22.23.3 либо проверенную совместимую более новую версию; не рассчитывать на системный Node старой версии.
5. В текущем checkout, с реальным `DEEPCURRENT_DB_PATH`, выполнить `npm run backup:db`. Это SQLite backup API, не копирование открытого `.sqlite` без WAL. Скрипт проверяет `quick_check` backup и сохраняет только БД, без чтения окружения или других файлов.
6. Достаточно места для рабочей БД, WAL, нового backup и старого release; проверить диск до сборки. Не хранить backup в Git. `backups/` и `.data/` содержат приватные данные.

## Shadow

Не поднимать параллельно старый и новый collectors с одним API/IP. Lease защищает только новые v2-процессы; старый процесс не знает о нём.

1. Установить зависимости из lockfile и выполнить `npm test`, `npm run lint`, `npm run build` в отдельном release/check-out. Не запускать две сборки в одной `.next`.
2. После согласованного окна остановить **существующий** collector; не удалять его PM2 definition. Web переключать только когда данные нового журнала уже проверены; на пустом новом журнале профили будут честно показывать pending.
3. Запустить новый код тем же единственным процессом с `DC_JOURNAL_MODE=shadow`, сохранёнными `DEEPCURRENT_DB_PATH` и прокси. `.env.local` сам по себе Node CLI не загружает: передать окружение через проверенную PM2 конфигурацию или Node `--env-file=.env.local`. Не отправлять вывод окружения в чат.
4. Новые таблицы аддитивны; legacy журнал, настройки, favorites и inbox остаются. Не переименовывать old aggregates в exact raw fills.
5. Запустить `npm run check:journal`. Требования: integrity `ok`, collector не stale, все заявленные markets acknowledged, нет растущего projection backlog, понятные recovery gaps/conflicts, диск не заполняется незаметно.
6. Проверить минимум 50–100 реальных кошельков против source fills и scoped state. Для unknown открытия не требовать придуманной даты. Проверить закрытие/повторное открытие, несколько DEX, spot и отсутствие данных одного scope.
7. `npm run check:realtime -- http://127.0.0.1:3000/api/live 1000 60000` запускать в согласованное тестовое окно: это реальная дополнительная нагрузка. Не принимать результат за нагрузку 1000 разных браузеров/профилей.
8. Проверить публичный proxy: SSE не буферизуется, idle timeout подходит, финансовые ответы не кэшируются service worker/CDN. Проверить фактическую мобильную сеть, а не только `200 OK` на localhost.
9. В shadow бот не читает Telegram updates и не отправляет Telegram/Web Push. Остатки старой outbox также не доставляются этим режимом.

Не считать `indexedWallets=1000` синонимом `exactUsers=1000`: обычный публичный API сохраняет ограничение десяти приоритетных адресов.

## Live только после приёмки

- Явно согласовать переключение и заменить `DC_JOURNAL_MODE=shadow` на `live` у единственного collector; перезапустить его с обновлённым окружением.
- Проверить текущие настройки пользователя и каналы. Для ручного end-to-end сообщения заранее получить разрешение владельца чата/подписки.
- History/shadow imports не должны массово превратиться в новые уведомления. Нельзя менять старым fills mode на `live`.
- Проверить durable retry/failed delivery отдельно от появления события в ленте. Провайдерский timeout может оставить неоднозначность фактической доставки.
- Проверить места, где прежняя версия показывала приблизительную дату/нулевые позиции как факт; не возвращать эти fallback ради красивого результата.

## Rollback

1. Остановить новый collector, сохранив БД/WAL и вывод диагностик без секретов.
2. Вернуть предыдущий проверенный release и прежнюю конфигурацию web/collector, сохранив тот же постоянный диск и окружение.
3. **Не восстанавливать старый backup поверх рабочей БД:** новые raw events, избранное и настройки после backup иначе будут потеряны. Restore проверять в отдельный файл.
4. Проверить ровно по одному процессу, HTTP/Telegram health и отсутствие второго ingestion writer. Новые таблицы оставить для разбора и последующего replay.

Для приёмки PostgreSQL/Redis нужен отдельный migration/rollback runbook с проверкой паритета. Этот документ не устанавливает и не выдаёт SQLite за PostgreSQL.
