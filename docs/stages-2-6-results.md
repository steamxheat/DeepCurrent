# Этапы 2–6: реализация и контрольная точка

Дата: 13 октября 2026. Это отчёт о локальной реализации, не акт приёмки production и не обещание точных сигналов всех 1000 адресов за 3 секунды.

Продолжение после ограничения бюджета: [бесплатный режим](free-data-mode.md). Текущий набор — 92/92 локальных теста. Значения ниже относятся к исходной контрольной точке; результаты новой очереди подтверждений записаны отдельно.

## Изменения, исправляющие причины ошибок

- Raw ID: `hyperliquid:mainnet:wallet:rawCoin:exchangeTime:tid`. Два tid одной миллисекунды не теряются; обе стороны между отслеживаемыми адресами сохраняются.
- REST обогащает существующий fill, не добавляет вторую сделку. Конфликт размера/цены/startPosition делает событие observed, а не молча заменяет доказательство.
- Raw запись и очередь расчёта атомарны; state, lifecycle, materialized closed trades и signal group фиксируются одной транзакцией. При сбое расчёт повторяется по сохранённым входам.
- Повторный replay не отправляет неизменившуюся старую историю в live. Большая догрузка не превращается в мегабайтный SSE delta: live ограничен, полный журнал доступен через `/api/events`.
- Decimal signed size считается строковой арифметикой BigInt; исходные числа не теряют десятичные знаки. Усреднённые цены/PnL отображения остаются Number, не бухгалтерской fixed-point моделью всего продукта.
- Точное событие исполнения не доказывает полноту всей позиции. Ambiguous tie, разрыв цепочки, конфликт, stale snapshot и отсутствующее начало остаются отдельными причинами unknown.
- Полный пустой scope очищает только свой рынок; ошибка одного DEX сохраняет его последний снимок как stale. Поздний ответ не перетирает более свежий.
- Coverage хранит доказанные интервалы отдельно: несвязанные диапазоны не соединяются через отсутствующие данные. Recovery не объявляет пустой старый API-диапазон доказательством полноты.
- Суммы и открытые позиции видимой страницы обновляются компактным POST каждые 10 секунд. Скрытая вкладка прекращает запросы; lease истекает через 30 секунд. История/график обновляются явно кнопкой, без повторной передачи всей истории каждые 10 секунд.
- Outbox сохраняет lease/retry, отделён от приёма fills; history/shadow не инициируют внешние сообщения. После провайдерского timeout редкий дубль внешнего сообщения возможен: Telegram не даёт общей exactly-once транзакции с нашей БД.

## Что проверено

- 80/80 локальных тестов, ESLint без замечаний, production build, `git diff --check`.
- 26/26 профильных тестов на реальном Mac mini Ubuntu / Node 22.23.3 в `/tmp/deep-current-journal.ykFw0H`, с отдельными временными SQLite. Рабочие сервисы и production БД не менялись.
- Backup/restore, crash перед projection, rollback внутри projection, дубликаты, поздние fills, конфликт, saturated timestamp, disjoint coverage, scope timeout/empty, decimal zero/flip, fee/rebate/currency, durable outbox, непрерывная и прерванная группировка oid.
- Browser QA: профиль загружается; сортировка открытий работает без перезагрузки страницы; mobile 390×844 без переполнения; разные подтверждённые открытия, явно неизвестные даты; маленькие суммы не округлены в ложный `$0`.
- Реальный API/WS в shadow. Никаких тестовых Telegram/Web Push сообщений пользователю не отправлялось.

## Измерения, не гарантии

Изолированный benchmark на самом Mac mini, 1000 адресов / 10 000 synthetic raw fills:

| Операция | Время |
|---|---:|
| Запись пакетами по 10 | 4,01с |
| Построение 1000 проекций | 4,03с |
| Чтение 1000 состояний + fills | 207мс |
| p95 записи пакета 10 fills | 9,31мс |

Это конечный burst, не обещание такой же задержки каждого события при постоянной нагрузке.

Локальный HTTP fan-out, 1000 SSE connections, 60 секунд: 0 ошибок. Финальный прогон после исправлений: 302 distinct events, p95 первого получения 1161мс, emit→client 37мс, подтверждённых обновлений lifecycle 1104мс, старт соединения 433мс. В другом прогоне при догрузке exact updates достигали 13 032мс. Это события активных адресов в конкретную минуту, не проверка exact-охвата 1000 кошельков. Повторные revision updates имеют отдельную задержку, поэтому их нельзя смешивать с первым BUY/SELL. Предыдущий стресс-тест обнаружил 12-секундную задержку и блокировку чтения профиля; они не скрыты за успешными unit tests.

Повтор с явным счётчиком охвата: 208 distinct events от 21 адреса, exact updates только одного активного адреса за минуту; 1000 подключений, 0 ошибок, p95 distinct event 1108мс, confirmed 1129мс. Этот результат особенно **нельзя** выдавать за 1000 проверенных exact-кошельков.

Компактное обновление профиля: HTTP 200, 9025 байт, 2,6мс локально; полная страница перед этим — около 1,5МБ. Это не замер мобильной сети/Tailscale. Обновление не должно заново скачивать полный HTML/RSC-график.

## Блокирующие условия для обещанного продукта

1. **Источник full fills.** Публичный API допускает 10 уникальных user WS-подписок на IP; REST weight 1200/мин не превращается в точный опрос 1000 адресов каждую секунду. Нужен легальный full-fill stream с startPosition/tid/fee/oid и replay либо отдельная подходящая node-инфраструктура. Ключ/тариф/инфраструктура ещё не выбраны.
2. **Хранение и приёмка этапа 6.** Нужны согласованный rollout PostgreSQL/Redis, перенос пользователей/избранного/журнала с доказанной сверкой, архив/retention, измерение bytes/day. Перемена названия БД не исправит лимит источника. Для внедрения в production требуется отдельная приёмка и безопасное окно переключения.
3. **Длительная проверка.** 24–72 часа shadow с тем же прокси, 1000 различными активными профилями и целевыми данными; p95/p99 каждого участка, drift, gaps, 429 и disk budget. Минутный SSE-тест не заменяет её.
4. **Исторические критерии.** Старый bundled screening не перепроверен новой версией финансовой арифметики; нельзя заявлять, что все 1000 сегодня гарантированно проходят winrate/PnL критерии. Copyability пока model, не реальное воспроизведение исполнения с задержкой.

Диск не очищается автоматически: source evidence нельзя удалять без проверенного архива. Collector останавливается при свободном месте <1GiB. Это предохранитель, не выполненная стратегия долгого хранения.

## Проверенные источники

- [API limits](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/rate-limits-and-user-limits): user subscriptions, weight, messages/IP.
- [Info endpoint](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint): последние 10 000 fills, страницы до 2000, включительные границы.
- [Node schemas](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/nodes/l1-data-schemas): node trades содержат start_pos/oid, полный raw-поток требует отдельного бюджета диска.
- [Latency guidance](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/optimizing-latency): требовательность низколатентной node-конфигурации. Не запускать такую ноду на имеющемся Mac mini без расчёта ресурсов.
